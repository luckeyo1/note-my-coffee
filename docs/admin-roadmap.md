# 관리자 페이지 로드맵

`admin.html` / `admin.js`를 앞으로 어떻게 키울지에 대한 계획. 무엇을 만들지보다
**왜 그 순서인지**를 남기는 게 목적이다. 화면 사용법과 접근 제어는 [`ADMIN.md`](../ADMIN.md),
계측 이벤트 정의는 [`docs/funnel.md`](./funnel.md)에 있다.

## 현재 상태

기록 추이 · 활성화·유지 퍼널 · 신규 사용자 유입 · 주간 리텐션 코호트 ·
요일×시간대 활동 · 모드 분포 · 평점 분포 · 인기 원두 TOP 10 · 최근 기록.

"제품이 어떻게 쓰이나"와 "마케팅이 되고 있나"에는 답할 수 있게 됐다.
다음 과제는 **이 페이지를 계속 쓸 수 있게 만드는 것**이다.

---

## 가장 시급한 것은 새 지표가 아니라 구조

`admin.js`는 `getDocs(collection(db, 'recipes'))`로 **컬렉션 전체를 내려받아**
브라우저에서 집계한다. 문제는 레시피 문서에 사진이 **base64 문자열로 같이 들어
있다**는 점이다(`main.js`가 `readAsDataURL`로 만든 data URI를 문서 필드에 저장).

**이 다운로드는 피할 수 없다.** 클라이언트 SDK에는 필드 선택(projection)이 없어서,
`admin.js`가 받은 직후 `delete data.imageUrl`로 버리더라도 **전송은 이미 끝난 뒤다.**

### 규모 추정

- 사진 1장의 base64 길이 ≈ **400KB**
  (`main.js`는 1600px·품질 0.72로 먼저 압축한다 → 대략 300KB 바이너리,
  base64가 약 33%를 더한다. 하드 상한은 `BUDGET = 950KB`)
- 사진 첨부율 30% 가정

| 누적 기록 | 대시보드를 한 번 열 때 다운로드 |
|---|---|
| 500건 | 약 60MB |
| 2,000건 | 약 240MB |
| 5,000건 | 약 600MB |

모바일에서는 사실상 열 수 없게 되고, Firestore 읽기 비용도 **열 때마다 전체 문서
수만큼** 청구된다. 즉 **기록이 쌓일수록 = 앱이 잘될수록 대시보드가 먼저 죽는다.**

`ADMIN.md`의 "알아둘 한계"도 같은 문제를 지적하며 **Cloud Functions 일별 집계**를
처방한다. 방향은 같지만 Functions는 Blaze(유료) 플랜이 필요하다.
아래 Phase 1은 **Functions 없이 클라이언트 쓰기만으로** 같은 목적을 달성하는 경로다.

## Phase 1 — 집계 구조로 전환 (최우선)

레시피를 저장할 때 카운터를 함께 올려두고, 대시보드는 원본 대신 그 집계를 읽는다.

### 새 컬렉션

| 컬렉션 | 문서 단위 | 담는 것 |
|---|---|---|
| `users/{uid}` | 사용자 1명 | `firstSeenAt`, `lastSeenAt`, `recipeCount` |
| `stats_daily/{YYYY-MM-DD}` | 하루 | `count`, `espresso`, `drip`, `successCount`, `ratingSum`, `ratedCount`, `newUsers` |

### 훅 지점

`storage.js`의 `saveRecipe()` — `addDoc`이 성공해 `docRef.id`를 돌려주는 자리.
`increment()`로 원자적으로 올린다.

**집계 쓰기가 실패해도 레시피 저장은 성공으로 유지한다.** 계측이 부가 기능이라
`track()`이 절대 throw하지 않는 것과 같은 태도다 — 부가 기능이 본 기능을 끌고
내려가면 안 된다.

### 효과

- 다운로드가 수백 MB → 수십 KB (일별 문서 365개 + 사용자 문서)
- `users.firstSeenAt`이 실제로 저장되므로 **"첫 기록일을 가입일 프록시로 쓴다"는
  현재의 한계가 사라진다**
- 코호트·휴면 계산이 O(전체 기록) → O(사용자 수)
- 최근 기록 카드만 `query(orderBy('date','desc'), limit(20))`로 따로 읽으면 된다

### 함께 설계해야 하는 것

- **과거 데이터 백필.** 관리자 페이지에 "집계 재생성" 버튼을 두고, **눌렀을 때만**
  전체를 한 번 읽어 집계를 다시 쓴다. 평소 경로에서는 전체 읽기를 없앤다.
- **정합성 복구.** 집계와 원본은 어긋날 수 있다(쓰기 실패·오프라인). 위 백필
  버튼이 곧 복구 수단이므로 둘은 한 세트로 만든다.
- ⚠️ **선행 조건 — Firestore 보안 규칙.** `users`·`stats_daily`에 대한 쓰기 권한이
  규칙에 없으면 이 Phase는 코드가 완성돼도 동작하지 않는다.
  규칙은 콘솔에서 직접 관리 중이므로(`ADMIN.md` 참고) **규칙 게시가 먼저다.**

## Phase 2 — 보는 것에서 하는 것으로

지금 카드는 전부 "관찰"이다. 마케팅 도구가 되려면 다음 행동으로 이어져야 한다.

- **휴면 위험군** — `users.lastSeenAt` 기준 경과일 분포와 규모. 리인게이지먼트
  대상이 몇 명이고 어느 구간이 급증했는지. Phase 1의 `users`가 있으면 거의 공짜다.
- **원두 인사이트 강화** — 지금은 빈도 TOP 10뿐이다. 여기에
  **급상승 원두**(직전 기간 대비 증가율)와 **실패율 높은 원두·모드 조합**을 더한다.
  전자는 제휴 상품 선정의 근거가 되고, 후자는 가이드 콘텐츠 소재가 된다.
  `success` 필드가 이미 있어 추가 데이터 없이 계산된다.

## Phase 3 — 열어봐야 아는 구조에서 벗어나기

지금은 관리자가 페이지를 열어야만 지표를 안다. **주간 요약 자동 발송**을 붙인다.

저장소에 이미 스케줄 워크플로 선례가 있다(`.github/workflows/bean-link-check.yml`).
같은 방식으로 주 1회 서비스 계정으로 집계를 읽어 요약을 이슈나 메일로 남긴다.
Phase 1의 집계 문서가 있어야 읽기가 가벼워 이게 현실적이 된다.

## Phase 4 — 획득 퍼널: 넣지 말 것을 권함

랜딩 방문·CTA 클릭·취향 검사는 **GA4에만 있고 Firestore엔 없다.** 이걸 admin에
가져오려면 GA4 Data API 파이프라인(서비스 계정 + 서버 함수)이 필요하다.

**권고: 당분간 만들지 않는다.** 서버 구성 요소가 하나 늘어나는 데 비해, 같은 정보를
GA4 탐색 보고서에서 이미 볼 수 있다. 대신 admin에 "획득 퍼널은 GA4에서" 링크를 두고
[`docs/funnel.md`](./funnel.md)의 탐색 설정 절차를 따르게 한다.
투자 대비 효용이 가장 낮은 구간이다.

---

## 왜 이 순서인가

**Phase 1은 나머지 전부의 전제다.**

- `users` 컬렉션이 생기면 Phase 2의 휴면 위험군이 거의 공짜가 된다
- 집계 문서가 생기면 Phase 3의 주간 요약이 가벼워져 현실적이 된다
- 반대로 Phase 1 없이 카드만 늘리면 **대시보드가 더 무거워져 붕괴가 앞당겨진다**

그래서 새 지표를 추가하고 싶은 유혹이 있어도 구조 전환이 먼저다.

## 측정 경계 (바뀌지 않는 것)

Phase를 모두 끝내도 아래는 그대로다. 화면의 안내 카드에도 같은 내용이 적혀 있다.

- **게스트 기록은 잡히지 않는다.** localStorage에만 있고 Firestore에 올라오지 않는다.
  로그인 시 `migrateLocalToCloud()`로 넘어온 것만 보인다.
- **`성공률`은 사용자 자기 평가다.** 추출 품질의 객관적 지표가 아니다.
- **랜딩·CTA·퀴즈는 GA4에서 본다.** (Phase 4 참고)
